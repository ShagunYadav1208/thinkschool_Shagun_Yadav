
# AI Reflection

Claude got the target right: the discount calculation in `OrderService` was the messiest code in piece 4 — the exact method where a `>=`/`>` boundary mixup earlier turned a $1000 order's total from 1230 to 1112 to 1171 before anyone caught it. Extracting it into `IDiscountRule` plus a DI-registered list means a new coupon or tier is one class and one registration line, not a re-read of a cascading switch. It also didn't over-engineer: no rule-priority system, no reflection-based auto-registration, just an interface and a sum. Where I'd have caught a bug: the summation assumes every rule stacks additively and registration order never matters. If a future rule needs to override another instead of adding to it — a coupon that replaces the bulk discount rather than stacking with it — this design silently does the wrong math. I'd catch that by testing rule *combinations*, not single rules in isolation, which the current tests don't do.

Full disclosure: I don't have GitHub Copilot wired up here, so I wrote the three comment-driven tests myself rather than accepting real Copilot suggestions — I'm not pretending otherwise. What comment-first testing reliably delivers, regardless of who writes the body, is a checklist: writing `// Test: validation rejects orders with negative quantity` before code forces you to notice which rules have zero coverage, which is how I found `ValidateItem`'s upper-bound check and `ValidateRequest`'s shipping-address check had never been tested.
