Real deadlock graph captured on Azure SQL Database, via a database-scoped Extended Events session
(trace flag 1222 and the error-log approach used in deadlock-graph.txt do NOT work on Azure SQL
Database - see AZURE-REPORT.md for why). Trimmed for readability: each process's internal engine
call-stack ("stackFrames") cut, same as deadlock-graph.txt. Every identifying field below (process
ids, spids, timestamps, lock resources, isolation levels, both sessions' real "inputbuf" SQL) is the
actual, unedited XML SQL Server wrote to the Extended Events ring buffer.

Session used to capture this:
  CREATE EVENT SESSION CaptureDeadlocks ON DATABASE
      ADD EVENT sqlserver.database_xml_deadlock_report
      ADD TARGET package0.ring_buffer
      WITH (MAX_MEMORY = 4096 KB, STARTUP_STATE = ON);
  ALTER EVENT SESSION CaptureDeadlocks ON DATABASE STATE = START;

  -- after the repro --
  SELECT CAST(target_data AS XML)
  FROM sys.dm_xe_database_session_targets st
  JOIN sys.dm_xe_database_sessions s ON s.address = st.event_session_address
  WHERE s.name = 'CaptureDeadlocks' AND st.target_name = 'ring_buffer';
